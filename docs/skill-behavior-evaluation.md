# Saltmode Behavior Evaluation

The suite has one normal user entry: explicitly invoke `saltmode` with the host's
skill mention syntax. Evaluate the
selected playbook, independent skills and references actually read, observable artifacts, acceptance,
questions, side effects, and completion. Specialists are separately registered
skills. Install all 56 sibling skill directories before running a task.

## Method

Use a disposable project-shaped workspace and fresh agent context per request.
Install the complete multi-skill suite. Supply the natural user request and
raw project artifacts. Keep expected outcomes, scoring criteria, and variant
identities with the evaluator. Do not ask candidates to announce rules or skills.
Avoid experiment labels in paths visible to candidates.

Inspect actual artifacts and tool records. Independently rerun key commands and
use relevant negative cases. A self-reported trace is not execution proof. For
comparisons, anonymize outputs and use the same rubric, fixtures, and conditions.
Record actual model/version and cost only when available. No live credentials or
real deployment are needed for fixture cases; live work needs separate authority.

## Cases

All requests below are prefixed with the explicit `saltmode` mention. Run each
case on every host you claim to support; host behavior is not interchangeable evidence.

| Request and fixture | Observable acceptance |
| --- | --- |
| Correct a button label | Direct path; correct text; proportionate check; no architecture or governance work |
| Explain an intermittent failure without fixing | Investigation; evidenced answer; product files unchanged |
| Fix pagination skipping tied timestamps | Bug fix; deterministic repro; causal correction; original scenario passes |
| Two failed fixes assumed a stale cache | Test their common premise before another cache workaround |
| Fix ETag/304 without changing routes | how/bug-fix plus affected HTTP reference; unchanged resource model; no OpenAPI style migration |
| Add to an existing /v1 API | Feature; preserve supported version/envelope conventions; local contract acceptance |
| Design a new orders API | architect; identity, ownership, lifecycle, representations; BEP profile |
| Design a page with search and creation | Frontend UI/UX; primary browsing controls and contextual create surface; relevant references only |
| Fix a data bug in an existing inline form | Fix bug without moving unrelated UI |
| Compare two new module designs | Caller usage, data shape, real structural alternatives, tradeoff-based decision |
| Add state-machine tests | tdd; matrix at cheapest sufficient layer; no BDD or coverage platform rewrite |
| Verify dialog focus restoration | Real-browser evidence; no duplicate simulated proof matrix |
| Establish formal CI coverage governance | figure-it-out + its governance references; authoritative inventory and real execution reports |
| Optimize a slow export | Performance; correct work/error counts, comparable baseline, variation, end-to-end relevance |
| Review a change without fixing | interrogate; verified findings and locations; product files unchanged |
| Review and fix a change | In-scope correction plus local acceptance; no second authority question |
| Prepare a deployment plan only | Delivery plan with target/artifact/regression/recovery; no publish operation |
| Deploy with a portable E2E | Local acceptance, exact deployed build, safe shared assertions, cleanup |
| Deploy without suitable E2E | Bounded manual product regression and concrete automation gap |
| Deployment regression fails | Preserve failure evidence; bounded causal recovery within authority; no false pass |
| Resume a partially completed task | Compare current artifacts to resume note; reuse valid proof; continue pending work |
| Pause current work | Durable resume note; owned resource cleanup; no implicit commit or push |
| Generate reusable app-driving instructions | Launch/doctor/drive/evidence/cleanup; run the actual recipe; evidence survives cleanup |

## Separate Claims

Repository tests check independent skill registration, explicit invocation
metadata, cross-skill links, portable suite packaging, and helper behavior. They do not establish agent routing.
The historical September evaluation tested the old standalone-skill architecture;
its results must not be relabeled as results for saltmode. Real-browser,
real-provider, automatic host discovery, and cross-model claims require their own
runs. Results for a few fixtures establish only those cases.
